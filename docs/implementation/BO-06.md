# BO-06 Implementation Note

Task ID: BO-06
Title: Implement Stage 2 constrained multi-objective BO
Branch: `main`

## Scope

BO-06 adds an opt-in constrained noisy multi-objective Bayesian optimizer for the
Stage 2 ASD virtual-lab problem. It does not change the existing simulator,
baselines, LLM adapter, or Stage 2 scenario semantics.

## Surrogate

`Stage2ConstrainedMOBOOptimizer` fits a transparent BoTorch `ModelListGP` with one
`SingleTaskGP` per measured outcome:

- GA thickness;
- negative NGA thickness;
- selectivity;
- negative process time.

The transformed signs make GA, NGA suppression, and process-time reduction
maximization-compatible while preserving measured outcomes in the run records.
Inputs are raw precursor dose, temperature, and cycle count with BoTorch
normalization. Outputs are standardized. The model uses `float64`, Matern kernels,
known-noise or inferred-noise mode, fit retries, and jitter escalation.

## Acquisition

The optimizer uses BoTorch's installed log-stabilized noisy expected hypervolume
improvement implementation:

```text
qLogNoisyExpectedHypervolumeImprovement
```

The implementation falls back to `qNoisyExpectedHypervolumeImprovement` on older
BoTorch releases. Outcome constraints are included in acquisition evaluation:

- GA thickness must be at least the YAML threshold;
- NGA thickness must be at most the YAML threshold;
- selectivity must be at least the YAML threshold.

The reference point is configured through `Stage2BOSettings.reference_point`. If not
provided, it is derived from configured feasibility thresholds and hard process-time
bounds, not from benchmark outcomes.

## Integer Variable Handling

Cycle count is handled as a true integer variable. The optimizer enumerates configured
or scenario candidate cycle counts, optimizes precursor dose and temperature
conditional on each fixed count, and compares acquisition values. It does not round an
unconstrained continuous cycle suggestion.

## Robustness

BO-06 implements:

- seeded Sobol initial designs;
- reuse of legacy ASD ledger rows through `observations_from_experiment_records`;
- duplicate and minimum normalized-distance checks;
- hard safety validation before accepting candidates;
- fit retries and numerical jitter escalation;
- random hard-safe fallback candidates;
- explicit fallback logging in proposal records;
- posterior summaries, feasibility probability, acquisition value, duplicate count,
  fallback use, hypervolume by iteration, and optimizer wall time.

The fallback is "feasible" with respect to known hard parameter safety. Outcome
feasibility is only known after simulation.

## Remaining Limitations

- The optimizer is tutorial-scale and CPU-oriented.
- The current fallback candidate is hard-safety-feasible, not guaranteed
  outcome-feasible before measurement.
- Hypervolume is computed from observed feasible points and a configured reference
  point; it is not an oracle hypervolume.
- The log-EHVI fused C++ extension was not available in this Windows environment, so
  BoTorch used its pure-Python fallback.
- Python 3.14 compatibility remains unverified locally; verification uses bundled
  Python 3.12.13.
